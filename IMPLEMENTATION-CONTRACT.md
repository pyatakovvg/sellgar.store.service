# Store: учетные записи и product_srv_v2

- Основание: запрос пользователя 2026-10-12 и принятые решения RFC конструктора.
- Ветка: master. До работы Store и gateways чистые; изменения admin UI вне scope.
- Владелец: store_srv; product_srv_v2 остается владельцем каталога.

## Scope

Сохраняем одну связь store_offer с каталоговым вариантом. Внутри нее создаются
учетные записи с UUID, уникальным артикулом, коллекцией произвольных текстовых
уточнений и отдельным остатком. У store_product и store_offer артикула нет.
Количества и движения адресуют учетную запись. Карточка не изменяет остаток.

Обновляем snapshots под события schemaVersion=3 от product_srv_v2,
локальные FK и целостность принадлежности варианта товару. Каталоговые поля,
опции и изображения не копируем в Store. Inbox/outbox сохраняем.

Транспортные DTO, команды приложения, ORM-модели и сущности ответа разделены.
DTO/команды валидируются class-validator и преобразуются class-transformer.
Изменение схемы выполняется явными миграциями, synchronize выключен.
Пользователь разрешил пересоздать локальные таблицы: данные store_srv
сбрасываются, после чего применяется начальная миграция новой модели.
Существующие UUID каталога не подменяются UUID v2.

Непосредственные gateway-потребители измененного Store-контракта адаптируются
вместе с сервисом. Frontend формы и новый order/cart lifecycle вне этой задачи.
Цена остается у store_offer: перенос цены на учетную запись не утвержден.
Дробные количества, партии и автоматическое распределение существующего
остатка между новыми записями не добавляются.

## Acceptance

- При создании связи с вариантом существует минимум одна учетная запись.
- Уточнения — строки value, без name, Property и PropertyOption.
- Уникальность артикула, принадлежность записей и неотрицательный остаток
  защищены базой и командами; точные технические решения описаны в README.
- Повтор команды не начисляет остаток повторно, конфликт версии и попытка
  изменить чужую запись откатывают транзакцию.
- Витринный ответ содержит учетные записи, их артикулы, уточнения и доступность.
- Архивированный каталог не попадает в витринное чтение.
- Проверены создание схемы миграцией, FK и транзакционные негативные сценарии.
- Проверены build/tests Store и затронутых gateways; runtime через RMQ,
  outbox/inbox и PostgreSQL. Сборка не заменяет проверки учета.

Commit/push и обновление gitlinks в эту задачу не входят.

Согласование 2026-10-12: один Nest-контекст с двумя RMQ microservices и одним
outbox relay, без HTTP listen; platform-express для штатного hybrid bootstrap.
